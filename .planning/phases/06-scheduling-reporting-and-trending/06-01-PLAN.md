       - Internal `pollForDueScans()`: queries control-plane DB for tenants where `scheduleFrequency IS NOT NULL`, `scheduleNextRunAt <= NOW()`, `isDeleted = false`, `status = 'active'`, `databaseName IS NOT NULL`. For each due tenant: if running count < 3, call `executeScan()`. Otherwise push to queue array.
       - Internal `executeScan(tenant)`: increments running counter. FIRST updates `scheduleNextRunAt` to computed next time (prevents re-pickup per PITFALL 1). Then creates audit run in tenant DB, calls `runAuditPipeline()`. In finally block: decrements running counter, if queue has items, `setTimeout` with 5-minute stagger to drain next.
       - Wrap entire `pollForDueScans` in try/catch that logs errors and continues (PITFALL 2).
       - The scheduler needs a valid access token for each tenant. For now, use a stub `getSchedulerAccessToken(tenant)` function that logs a warning and returns a placeholder. Document that token refresh (PITFALL 3 from research) is an open concern -- the existing TokenManager in audit-runner handles refresh within a pipeline run, but the initial token must come from stored credentials.
       - Import `runAuditPipeline` from `@omzig/audit`, `getControlPlaneDb` and `getTenantDb` from `@omzig/db`, `pushAuditProgress` from `../services/signalr.js`.

    4. Create test file `apps/api/src/__tests__/scheduler.test.ts`:

       - Test error swallowing in poll loop.
       - Test startScheduler/stopScheduler lifecycle.
