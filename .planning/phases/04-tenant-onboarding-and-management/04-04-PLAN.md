<objective>
Build the 5-step tenant onboarding wizard at /tenants/new that guides MSPs through connecting a new client M365 tenant via OAuth consent or GDAP delegated admin.

Purpose: This is the critical onboarding UX. Without it, MSPs have no way to connect client tenants to the platform. The wizard must handle both OAuth (shareable consent link) and GDAP (relationship ID verification) paths, then auto-provision the tenant database and trigger the first audit.

Output: Full-page wizard with 5 steps, onboarding state management hook with setupWizardState DB persistence, API client extensions for onboarding and wizard-state endpoints.
</objective>

    **useOnboarding.ts** hook:
    - State: currentStep (1-5), tenantId (string|null), connectionMethod ('oauth'|'gdap'|null), consentUrl (string|null), gdapResult (GdapVerificationResult|null), provisioningStatus ({ dbCreated, tokenStored, firstAuditTriggered } booleans), error (string|null), loading (boolean), lastSyncedAt (string|null for optimistic locking)
    - **Persistence strategy (per locked CONTEXT.md decision: "Uses existing setupWizardState table for step tracking and resume")**:
      - On mount: call `fetchWizardState()` to restore state from the setupWizardState table. If state exists and isComplete is false, hydrate currentStep, tenantId, connectionMethod from stepsCompleted metadata. Also cache in localStorage for instant hydration on same-session page refreshes (before the API response arrives).
      - On each step advancement: call `updateWizardState({ currentStep, stepsCompleted: buildStepsCompleted() })` to persist to the DB. The stepsCompleted array stores per-step metadata: `[{ step: 1, data: { tenantId, displayName, primaryDomain, contactEmail }, completedAt }, { step: 2, data: { connectionMethod }, completedAt }, ...]`. Also update localStorage cache.
      - On wizard completion (step 5 reached): call `updateWizardState({ currentStep: 5, stepsCompleted, isComplete: true })`.
      - On "Connect Another Tenant": call `resetWizardState()` to DELETE the setupWizardState row and clear localStorage cache.
      - localStorage serves as a session cache for fast hydration only -- the setupWizardState table is the source of truth.
    - `goToStep(step: number)`: validate step transitions (can only go forward if current step data is complete, can go back to 1-3). Persists via updateWizardState.
    - `submitTenantDetails(data)`: calls createTenant API, stores tenantId, persists step 1 completion to setupWizardState, advances to step 2
    - `selectConnectionMethod(method)`: stores method, persists step 2 completion to setupWizardState, advances to step 3
    - `generateConsent()`: calls generateConsentUrl(tenantId), stores consentUrl
    - `verifyGdapRelationship(relationshipId)`: calls verifyGdap(tenantId, relationshipId), stores result
    - `startProvisioning()`: calls provisionTenant with appropriate data based on connection method. For OAuth, the m365TenantId comes from the consent callback (stored in URL params). For GDAP, from the gdapResult.customerTenantId. Token is the m365TenantId itself for client credentials approach (per RESEARCH pattern 2).
    - On mount: check URL params for consent=success&tenantId={id} -- if present, restore state and auto-advance to step 4. Also persist this state transition to setupWizardState.
